# Frontera RuscaDB — 2026-11-01 (ciclo 7)

> Investigación aplicada a las specs SPEC-0183/0184. Cada técnica incluye la
> fórmula/complejidad que se implementó o que queda como siguiente paso.

## 1. Lógica de tres valores (SQL)

- **Estado del arte**: ISO/IEC 9075-2:2023 define `NULL` como ausencia de valor;
  las comparaciones producen `UNKNOWN`, y `WHERE` solo conserva `TRUE`. La
  lógica es la de Kleene (1952), con las tablas:

```text
x AND y: F si alguno es F; T si ambos T; U en otro caso
x OR  y: T si alguno es T; F si ambos F; U en otro caso
NOT U = U
```

- **Implementación**: `Truth { True, False, Unknown }` en `executor/eval.rs`.
  Evaluación con cortocircuito; coste por fila `O(|φ|)` y filtro `O(n·|φ|)`.
  No hay DNF ni productos cartesianos, así que no hay `O(n²)`.
- **Evidencia**: `tests/spec_0183_0184.rs` (AC-0183-01/02).

## 2. `DISTINCT` de O(n²) a O(n log n)

Antes: `unique.contains(row)` por fila → `O(n²·k)` comparaciones.
Ahora: clave canónica `κ(r)` (nombre + tag + bytes; `-0.0 → +0.0`, `NaN`
estable) y `BTreeSet<Vec<u8>>`:

```text
coste = O(n · k · log n)   (k = ancho de fila)
memoria = O(n · k)
```

Se preserva el orden de primera aparición con `retain`. Alternativa O(n) media:
`HashSet<u64>` con hash de 128 bits y verificación ante colisión; se descartó
para mantener exactitud determinista sin dependencias.

## 3. Prepared statements (protocolo extendido)

- **Estado del arte**: PostgreSQL separa `Parse` (una vez), `Bind` (valores) y
  `Execute`; el cliente nunca concatena SQL. SQLSTATE separa el código estable
  del mensaje.
- **Implementación**: `PreparedHandle` (texto + tipos + `plan_cache_key` FNV-1a
  64) y `execute_prepared` que renderiza literales escapados.
- **Complejidad**: `prepare O(L)`; `bind O(p)`; por ejecución se evita el
  `O(L)` de parseo. Una colisión de hash solo fuerza revalidar el texto, no
  cambia resultados.
- **Evidencia**: AC-0184-01/03.

## 4. Códigos de error estables

`RuscaError::code()` mapea cada variante a un identificador
`UPPER_SNAKE_CASE` (`RQL_PARSE`, `COLUMN_NOT_FOUND`, `TYPE_MISMATCH`, ...). El
contrato es el código, no la prosa; los tests fijan el mapeo (AC-0184-02).
Inspiración: SQLSTATE (PostgreSQL Appendix A) y los `ErrorKind` de Rust.

## 5. Siguiente frontera: joins de complejidad óptima

El hueco algorítmico mayor es el join. Un nested-loop es `O(|R|·|S|)`; un
hash-join es `O(|R|+|S|)` con memoria `O(min(|R|,|S|))`. Para consultas
multi-join, los **worst-case optimal joins** (Ngo, Porat, Ré, PODS 2018)
garantizan:

```text
O( N^{ρ*} )   con ρ* = min over fractional edge covers
```

frente a `O(N^{#relaciones})` del producto cartesiano. Es el siguiente paso para
`join_reorder` (hoy heurístico) y para `MATCH` multi-patrón.

## 6. Estadísticas y planificador

SQLite documenta `ANALYZE`/`PRAGMA optimize` para histogramas; sin ellos el
planificador elige por selectividad estimada. Propuesta: histogramas
equi-depth por columna y `ANALYZE` explícito, con coste de actualización
`O(n log n)` y memoria `O(b)` (b = buckets).

## 7. Verificación

- Mutation testing (DeMillo et al., 1978; Just et al., ISSTA 2014): el gate
  nightly exige MS ≥ 85 % (`cargo xtask mutation-score`).
- Tests de aceptación con nombres `test_ac_*` y `cargo xtask trace/contract`.
